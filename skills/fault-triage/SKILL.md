# 故障分诊技能（fault-triage）

把"机器不对劲"这种模糊报修，收敛成**可执行、可验证、安全先行**的排查路径。
本技能给排查思路与步骤，不替现场负责人做停机/拆修决策。

## 触发逻辑

- **触发方式**：设备出现异常，需要定位原因并给出排查/维修步骤。
- **触发示例**：
  - "CK6140 主轴一转就有金属摩擦声"
  - "加工外圆时尺寸忽大忽小，没有报警"
  - "刀塔转不停 / 卡盘夹不紧，帮我查查"
  - "FANUC 系统偶发 414 报警，重启又好"
- **不触发**：只问某个报警码含义 → `alarm-decode`；要保养/点检计划 → `pm-planner`；要登记报修或查历史 → `work-order`。

## 输入要求（信息不足先问诊，不要猜）

一次最多问 **2–3 个**最能切分原因空间的问题，优先顺序：

| 信息 | 为什么关键 |
|---|---|
| 设备型号 + 数控系统（FANUC / SIEMENS / 三菱 / 广数…） | 同报警码不同系统含义不同；备件与电路不同 |
| 具体现象 + 有无报警码/报警文字 | 有码走报警路径；无码走机械/工艺观察路径 |
| 发生时机（开机/加工中/换刀时；持续还是偶发） | 区分热相关、松动、干涉、参数/程序 |
| 最近变更（撞机、换刀/换料、改程序参数、维修后） | 很大比例故障由最近变更引入 |
| 历史是否出现过、如何恢复的 | 复发故障优先查工单/案例库 |

问诊用工人听得懂的话，给足选项（"是尖啸声还是沉闷的哐当声？"），不要一次抛五个问题。

## 工作流程（严格按序，不跳步）

1. **安全前置**：只要现象涉及运动部件、高压、液压或需要开盖/伸手，先给一句醒目安全提醒（停机、断电、LOTO、保持旋转部件静止），再谈排查。能在"运行中观察"完成的步骤与"必须断电"的步骤明确区分。
2. **分诊定性**：先判断大类——机械（主轴/导轨/丝杠/轴承/刀塔/卡盘/传动）、电气与驱动（电源/伺服/编码器/接线/IO）、液压气动（泵/阀/压力/泄漏）、冷却润滑、数控系统/参数/程序、工艺与刀具。用一两句说明分诊依据。
3. **查历史**：通过 machine-db 查同设备 `work_orders`、同现象/同报警码 `fault_cases`；有复发史优先指向既往根因。查不到不臆造。
4. **列可能原因**：按"可能性 × 排查成本"排序成表（先易后难、先外后内、先软后硬），每行给一句话机理说明和快速鉴别方法。
5. **分步排查**：每个排查步骤写成三要素——**怎么做** → **正常/异常怎么判定** → **异常下一步去哪**。优先给不需要专用仪器、不用拆大件的检查（看报警、看油位压力、听声定位、摸温、紧固、互换法、对刀法、查程序参数）。
6. **处置建议**：给出处理方向与所需备件/工具/资质；明确哪些属于操作工可处理、哪些必须报修、哪些应升级工程师/厂家。
7. **高危方案复核**：最终步骤若含带电、高压、旋转部件、液压储能、起重、热表面，先委托 **safety-reviewer** 子代理复核，再把其隔离/资质要求并入答复（见 SOUL 多智能体协作节）。
8. **沉淀（用户同意后）**：诊断闭环后，把"现象→根因→关键判据→处理"写入 machine-db 的 `fault_cases`，需要正式记录时用 `work-order` 开工单。

## 输出格式

- 使用 `templates/diagnosis_template.md` 的结构：安全前提 → 分诊结论 → 可能原因排序表 → 排查步骤（三要素）→ 处置建议与升级条件。
- 用表格呈现原因排序与判定标准；步骤编号，操作工可逐条照做并回报结果。
- 用户要求存档时，用 Write 写到 `/mnt/user-data/outputs/`，文件名 `诊断_{设备编号}_{yyyyMMdd}.md`。

## 禁止事项

- 禁止在现象、报警码、系统型号不明时直接断言唯一原因；给排序假设并说明鉴别方法。
- 禁止编造具体机型的电气参数、端子号、扭矩、报警码含义；不确定就写"按该机型维修手册核实"。
- 禁止省略或后置安全提醒；禁止给"可以不停电/不泄压先试试"的捷径。
- 禁止替用户决定停机、拆修、呼叫厂家；只陈述利弊与升级条件。
- 禁止把推测写成事实；每一步判定都要有可观察/可测量的依据。
