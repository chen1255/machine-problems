# 维修工单技能（work-order）

让每次维修都**有单可查、有史可溯、有案例可复用**。工单是结构化记录，不替代现场已有 EAM/MES 系统，用于本机演示与小型车间的轻量台账。

## 触发逻辑

- **触发方式**：报修登记、更新处理进展、完工回填、查某设备/某报警的历史、做停机与故障统计。
- **触发示例**：
  - "CNC-01 卡盘夹不紧，先报个修"
  - "2 号机上周那个 414 最后怎么处理的？"
  - "统计一下这季度各设备停机时间"
- **不触发**：还不知道原因需要排查 → 先 `fault-triage`；查报警码含义 → `alarm-decode`。

## 工单状态机（按序流转，不跳填）

`open（已报修）→ diagnosing（诊断中）→ resolved（已修复待验证）→ closed（验证关闭）`
旁路：`escalated（已升级厂家/工程师）`。每次状态变化都要有时间和内容，不能把未完成的维修记成已完成。

## 工作流程

1. **报修开单**：向用户收集设备编号（查 `machines` 核实）、现象、报警码、严重度（高=停机/安全；中=可带病限制运行；低=不影响生产）、报修人/班组；生成工单号（建议 `WO-yyyyMMdd-序号`），以 `status=open` 写入 `work_orders`。信息不全只补问关键字段，不阻塞开单。
2. **过程更新**：开始处理转 `diagnosing`，记录初步判断、已做检查、是否需要 LOTO（联动 `loto-safety`）、是否升级。
3. **完工回填**：与用户确认后填**根因**、处理措施、更换备件、停机时长（分钟）、是否验证恢复；先转 `resolved`，经试切/试运行确认后 `closed`。
4. **沉淀案例**：对有复用价值的闭环故障（根因明确、有关键判据），写入 `fault_cases`（现象/系统分类/报警码/根因/关键判据/解决措施/停机时长/关键词），并用来源工单号关联，供以后 `fault-triage` 检索。
5. **历史与复发查询**：
   - 按设备：`SELECT ... FROM work_orders WHERE machine_id=? ORDER BY created_at DESC`；
   - 按报警码/现象/系统：关联 `fault_cases` 做关键词检索；
   - 发现同设备同类故障反复出现时，主动提示"复发倾向"，建议排查深层根因而非只处理症状。
6. **统计（用 read_query 聚合，不臆造数字）**：设备停机总时长/MTTR、按系统分类的故障次数、报警码 Top 列表等；数字一律来自库内查询。
7. **导出**：用户需要时用 `templates/workorder_template.md` 生成单张工单/历史清单，Write 到 `/mnt/user-data/outputs/`。

## 输出格式

- 开单/更新后，用简短表格回执：工单号、设备、状态、已记录字段、下一步。
- 历史查询结果用表格：时间 / 设备 / 现象 / 报警码 / 根因 / 措施 / 停机 / 状态。
- 统计给出表格 + 一句客观结论（只陈述数据，不夸大）。

## 禁止事项

- 禁止编造根因、备件或停机时长；用户未提供的留空并提示补录，不得用推测填充完工字段。
- 禁止把 open/diagnosing 直接表述为已修复；状态必须与实际进展一致。
- 统计数字必须来自 SQL 查询结果，禁止估算后冒充库内数据。
- 案例库只收录已闭环且根因明确的故障；存疑、未验证的不写 fault_cases。
- 涉及人员隐私/考核的信息不录入，库中只保留班组/工号等作业信息，不做个人评价。
